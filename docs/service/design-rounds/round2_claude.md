## New live facts that change Round 1 (VERIFIED, 2026-10-26, head ≈ 98.81M)
1. **Topic-only `eth_getLogs` (no `address` filter) is capped at 30,000 blocks per query** on rpc.mainnet.chain.robinhood.com. Error text: "query spans N blocks … but only 30000 are allowed for this request; narrow the block range, or add an address filter". Codex's cost formula `ceil(span/9,999,001)` is wrong for per-wallet scans; the correct cost is `ceil(span/30,000)`. Measured: 34 windowed calls over 1M blocks (~1.2 days at 100 ms) returned in 0.1 s on a cold bucket and 7.5 s once the 14/s throttle engaged. So: a 7-day victim window ≈ 202 calls ≈ 15 s; full chain history (≈99M blocks) ≈ 3,300 calls ≈ 4 min. A per-wallet scan is feasible as a background job, NOT inside a 20 s free screen; the victim's incident time must bound the window, and the report must state the window.
2. **`safe` and `finalized` tags are supported** by the RPC: latest 98,814,277; safe 98,809,044 (−5,233 blocks ≈ 9.3 min); finalized 98,805,255 (−9,022 blocks ≈ 15.9 min). `eth_getLogs` accepts `"safe"` as a block tag. This resolves Codex's UNSURE; the two-cursor design (provisional=latest, evidence=finalized) is implementable as proposed.
3. **Blockscout address endpoints work but are slow**: `/addresses/{a}/token-transfers?type=ERC-20` 50 items/page in 4.5 s; `/addresses/{a}/transactions` 50/page in 3.3 s; `/addresses/{a}/logs` 0.6 s. Usable as a secondary source for native/internal transfers only, never the primary source of evidence (slow, Cloudflare-fronted, unversioned).
4. **PonsV2LaunchAndBuy (0xe33e9e47…) is verified on Blockscout** with `event Launched(address indexed token, address indexed curve, address indexed recipient, address launcher, uint256 quoteSpent, uint256 tokensReceived)` and write functions `launchAndBuy`, `rescue`, ownership. A real recent launch receipt had 9 logs across the token, the curve/market (0x3c1ebae3…), 0x31ea5b45…, 0x7ed598bc… and the launcher. The snipe-tax-waiver list from the ring case is therefore in calldata/curve events, not in `Launched` itself — the "exempt wallet" signature needs the curve ABI (UNSURE until fetched). The ring signature that IS cheaply computable from existing Sleuth data: "≥10 distinct buyers in the launch block or the next 3 blocks that collectively hold ≥50% of supply" (bundled buy), from the Transfer logs Sleuth already collects.

## Where I challenge Codex
**C1. Architecture (Option B, Supabase Postgres + VM) is over-built for the pilot Codex itself describes.** Codex's own stop criteria assume fewer than 10 paid cases/month. One FastAPI process + one worker process + SQLite in WAL mode behind a repository interface handles that with zero managed services, no network DB, and trivial backup (copy one file). Bo has operated several Supabase projects that got paused or wedged; a managed Postgres is one more thing to keep alive for a product whose demand is unproven. The brief also forbids production deployment and spending in this phase. Counter-proposal: SQLite WAL now, repository layer so Postgres is a swap, and Codex's queue semantics (lease, heartbeat, `BEGIN IMMEDIATE` instead of `SKIP LOCKED`) kept intact. Codex: where does SQLite actually break in this design — be specific (webhook writer + worker writer contention? backup during long scans?).

**C2. Cutting x402 entirely conflates two uses.** x402 for *case creation* is stateful and risky (Codex is right: a signature must not start a long job). x402 for a *stateless screening call* (`POST /v1/screen/token`, `exact` scheme, Base USDC, ~$0.10, response is the same free triage JSON) has no job, no entitlement, no reconciliation beyond the facilitator receipt, and serves the customer the skeptic and I both think is more real: bots, wallets and launchpad tooling that want a pre-trade check. Counter-proposal: x402 only on stateless screening; human checkout only for cases. Codex: what breaks?

**C3. "$49 rug investigation" vs "show findings first".** The skeptic's point stands: a victim who sees a paywall before any finding bounces. My proposal: free screening shows the full verified findings (what Sleuth triage already produces in 20 s). Payment buys the persistent case workspace, the deeper trace/dev-history passes, the evidence export, and 30 days of monitoring. Price: $29 one-time case + optional $9/month monitoring extension, not $49. Codex: is a $29 price below the floor given your human-support cost estimate (15 min/case = unprofitable)? If so, what must be automated to make $29 work, or should it be $49 with a hard "no human support" rule?

**C4. Wallet-drain: cut, or ship narrowly with an explicit coverage statement?** Codex says cut until native-internal and historical-7702 coverage exist. I say the honest version is shippable: ERC-20 Transfer-from-victim + Approval-by-victim over a victim-bounded window (fact 1), live 7702 delegation check with cache bypass and delegate target extracted, top-level native sends from RPC transactions, and an explicit `coverage.gaps` entry: "internal native transfers: unknown (explorer-dependent)", "historical 7702 authorizations: unknown (no index)". That is exactly the three-valued standard the repo already uses. Codex: name the specific drain shape where this narrow collector would produce a *wrong* (not merely incomplete) finding.

**C5. LLM narratives.** I proposed an LLM narrative layer with mandatory evidence IDs. Codex says none. I concede for the MVP: deterministic templates only. Record as resolved.

**C6. Permit premise.** Codex is right that EIP-2612 `permit` emits `Approval`. Correction accepted. Permit2 SignatureTransfer remains a gap → "unknown" verdict.

**C7. Codex missed one place where deadlines lose evidence that I verified: `trace.wallet` discards the whole wallet dict on timeout.** Codex listed it; agreed. But Codex's fix ("checkpoint after each span") does not cover the receipt-fetch loops (`tx_records_full`, devhistory RECEIPTS_CAP) which also discard on budget. Any collector refactor must return partial receipt sets too.
